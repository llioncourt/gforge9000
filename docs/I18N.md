# Internationalization (i18n)

## Architecture

| Piece | Location |
| --- | --- |
| Language registry (codes, names, direction, fallback, aliases) | `src/i18n/config.ts` |
| i18next instance factory (backend, fallback, missing-key policy) | `src/i18n/index.ts` |
| React provider + `useLocale()` | `src/i18n/provider.tsx` |
| Locale detection & persistence (cookie + localStorage) | `src/i18n/detect.ts` |
| Lazy namespace loading + pseudo-localization | `src/i18n/resources.ts` |
| Locale-aware formatters (dates, numbers, currency, bytes, duration) | `src/i18n/format.ts` |
| Hooks: `useT()`, `useFormatters()` | `src/i18n/hooks.ts` |
| Translation catalogues | `src/i18n/locales/<locale>/<namespace>.json` |
| Key typing (English is the source of truth) | `src/i18n/types.d.ts` |
| Language selector | `src/components/app/language-selector.tsx` |

Library: **i18next + react-i18next** (a single instance, created once per client
session and once per SSR render — never inside a component render).

## Languages

- `en` — English (default and fallback language)
- `pt-BR` — Português (Brasil), falls back to `en`
- `en-XA` — pseudo-locale, **development only** (`import.meta.env.DEV`)

Language precedence:

1. explicit choice saved on the user's account (`profiles.preferences.locale`)
2. explicit choice saved in the `ucf_locale` cookie (also read during SSR)
3. explicit choice saved in `localStorage` (`ucf.locale`)
4. browser / `Accept-Language`
5. `DEFAULT_LOCALE` (`en`)

Because the cookie is read on the server, the first server-rendered HTML is
already in the right language — no wrong-language flash.

## Namespaces

One JSON file per namespace per locale:

`common`, `navigation`, `errors`, `auth`, `dashboard`, `characters`,
`campaigns`, `lore`, `media`, `library`, `packs`, `rules`, `settings`,
`battle`, `dice`, `marketing`.

`common`, `navigation` and `errors` are bundled with the app shell (they are
needed before any route renders). Every other namespace is code-split and
fetched the first time a screen asks for it (`src/i18n/resources.ts`), then
cached — one request per namespace per locale, per session.

## Using translations

```tsx
import { useT, useFormatters } from "@/i18n/hooks";

function Example({ character }: { character: Character }) {
  const { t } = useT("characters");
  const f = useFormatters();

  return (
    <>
      <h1>{t("sheet.title", { name: character.name })}</h1>
      <p>{t("sheet.points", { count: character.points })}</p>
      <p>{f.date(character.created_at)}</p>
    </>
  );
}
```

Rules:

- Never concatenate translated fragments — one key per sentence, with
  interpolation (`t("lore.deleteConfirm", { name })`).
- Plurals use i18next suffixes (`key_one` / `key_other`), never `n === 1 ? …`.
- Markup inside a sentence uses `<Trans>` from `react-i18next`.
- Dates/numbers/currency/byte sizes go through `useFormatters()`; no hardcoded
  `MM/DD/YYYY`, no manual decimal-separator swapping.
- Currency is a property of the data, never of the interface language.
- Enum/status values stay structural in the database (`draft`), and are
  translated for display: `t(\`status.${status}\`)`.
- Accessibility text (`aria-label`, `title`, form labels, validation messages)
  is translated too.
- Do **not** translate user content, proper names, IDs, slugs, URLs,
  file names or technical values.

## Key naming

`namespace:section.item`, semantic and stable:

- `common:actions.save`, `common:states.loading`
- `navigation:links.campaigns`
- `characters:sheet.attributes.title`
- `lore:entity.deleteConfirm`

Never `text1`, `label23`, whole English sentences as keys, or hashes.

## Missing translations

- The current locale is tried, then the fallback locale (`en`), then the
  `common` namespace.
- If a key is still missing, `parseMissingKeyHandler` renders a humanized
  version of the last key segment (`lore.revealEntity` → “Reveal entity”), so a
  raw key is never shown to a user.
- In development, a deduplicated `[i18n] missing translation …` warning is
  logged. In production nothing is logged and nothing breaks.

## Adding a language

1. Add an entry to `LOCALES` in `src/i18n/config.ts` (code, names, direction,
   fallback, aliases, Intl locale).
2. Create `src/i18n/locales/<code>/` and copy the English namespace files.
3. Translate them.
4. Run `bun run i18n:check`.

No component changes are required; the selector, engine and formatters all read
the same registry. `dir` is applied to `<html>`, so an RTL locale works without
architectural changes.

## Adding a key / namespace

- Key: add it to `src/i18n/locales/en/<ns>.json` **and** every other locale,
  then use it. English typing drives autocomplete (`src/i18n/types.d.ts`).
- Namespace: add the name to `NAMESPACES` in `config.ts`, create the JSON file
  in every locale, and add it to `types.d.ts`.

## QA commands

```bash
bun run i18n:check    # missing/extra keys, empty values, invalid JSON, structure mismatch
bun run i18n:scan     # reports user-facing strings still hardcoded in components
```

`i18n:check` exits non-zero when a locale is missing keys present in English,
has keys English doesn't have, contains empty strings, or diverges structurally.

## Pseudo-localization

In development, pick “Pseudo” in the language selector (`en-XA`). Every
English string is accented and padded ~30% (`[Sávé·····]`), which exposes
hardcoded strings (they stay plain) and layouts that break with longer text.
The locale is disabled in production builds.
